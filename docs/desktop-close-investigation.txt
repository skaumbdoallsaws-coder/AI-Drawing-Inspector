Ranked findings (line numbers in this section refer to the PRE-CHANGE source)

1. Synchronous browser suspension failure can permanently latch transition.
   desktop/src/application-main.cjs:107 sets transition = true; line 108 calls
   browser.suspend BEFORE entering try at line 109. A synchronous exception
   never reaches the catch or finally. Every later change returns at line 106.
   desktop/src/research-pane.cjs:302 calls publish from suspend; line 111 sends
   to native chrome/splitter webContents. A stale/destroyed view can throw here.
   This precisely fits no dialog, a live backend, and a responsive renderer.
   It requires an initialized research pane; the incident does not establish
   whether one had ever been opened. An attached pane is not a separate visible
   top-level window. The old finally's resume call at line 135 could also throw,
   but it ran AFTER clearing transition, so it did not itself latch that flag.

2. The FIRST close can hang in browser/document cleanup before stopping backend.
   application-main.cjs:130 sets closing, then lines 132 and 90-103 await
   shutdown. Lines 93-96 await browser construction, pane.dispose and
   documents.dispose before runtime.stop at line 97. None had a deadline.
   research-pane.cjs:17, :57 and :299 await construction/proxy/navigation;
   :320-321 await connection/storage/proxy disposal. document-preview.cjs:105
   awaits session connection/storage cleanup. Any unresolved promise here
   leaves the main window and backend alive without creating a dialog.
   This also requires browser/document initialization and fits the first
   observed WM_CLOSE. Important distinction: with closing already true, the
   old native close/before-quit handlers at application-main.cjs:193 and :241
   STOP preventing default. Another native X could bypass cleanup; File > Close
   still silently returns at line 106. Thus closing=true is not proof that a
   second WM_CLOSE would have been swallowed.

3. A previous native reload/restart can leave transition true forever.
   application-main.cjs:119 awaits loadURL; :126 awaits runtime.restart;
   :135 clears transition only when execution reaches finally. Later close
   events are prevented at :193/:241 and discarded by :106.
   The meaningful navigation promise is loadURL; Electron webContents.reload
   is a fire-and-forget API, so await reload() does not await page completion.
   runtime-supervisor.cjs:308 waits for starting, and :314 chains stop then
   start. stopOwned itself has 15s graceful + 5s forced waits (:52, :197-204),
   but stop's starting dependency can be stuck, including response-reader
   cleanup (:43). Application startup has a 120s allowance (:161), so an
   ordinary restart can also be long. Lower likelihood if the only reloads
   were facility-session reloads, as reported: those do not enter change().

4. An undisplayed or unresolved native dialog can hold the transition.
   application-main.cjs:111 awaits Unsaved work; :117 awaits a blocker message;
   :127 awaits a restart-error message; :134 awaits a general-error message;
   :99 awaits a cleanup warning. message at :87-88 had no timeout. Even an
   observation timeout at :77 routes into that unbounded message await.
   The absence of a visible native dialog makes an ordinary user-decision
   wait less likely, but does not rule out an unresolved dialog API call.
   Saved describes the facility document, not the entire observer: unchanged
   static/index.html:22321-22337 aggregates dirty/busy/pending across workflows.
   Assembly animation/rehydration and other workflow flags are included at
   :22359-22381. A loaded 3D model alone is not a blocker (:22358).
   A valid busy/pending result, invalid observation, changed fingerprint, or
   explicit Cancel intentionally keeps the window open (application-lifecycle
   .cjs:2-22). Those rules were retained. Alone they should produce a reason
   or an explicit cancellation; they explain silence only with another fault.

5. Shutdown exceptions leave closing sticky; late shutdown stages can hang.
   After application-main.cjs:130, any rejected disposal, stop, evidence write,
   window.destroy, or app.quit enters :134, which does not reset closing.
   Even after a dismissed error dialog, File > Close returns silently at :106.
   An unresolved evidence write at :101-102 also prevents destruction. These
   are weaker explanations for a still-live backend if stop already finished.
   The native handler distinction described in finding 2 still applies.

6. Startup and automation have additional gates, unlikely after three hours.
   booted starts false (:16), becomes true only after initial loadURL (:213-214),
   and is never reset by a facility session or 3D view. Close while !booted was
   silently discarded (:106), including an initial navigation that never
   completed. The window normally starts hidden, but second-instance handling
   can show it (:156). Acceptance cleanup sets closing before shutdown (:238).
   Interactive startup failure awaits a dialog and runtime.stop (:245-247);
   automated failure sets closing (:251) and awaits cleanup/report writes
   (:254-265). These are separate startup/acceptance routes, not an explanation
   for a normally booted three-hour interactive run.
