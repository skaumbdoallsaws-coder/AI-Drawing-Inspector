# Sage research-to-layout delivery plan

Created: 2026-09-17. Schedule revised: 2026-09-23.

Current user deadline: 40 days remain to record the facility-layout workflow for
Y Combinator. This supersedes the earlier two-week public-demo planning assumption.
The target is a generally usable research-to-layout beta within a declared scope;
the recording should show ordinary product behavior, not a special execution path.

## Product requirement

Sage must accept incomplete or complete manufacturing briefs, obtain applicable
project/catalog knowledge, research consequential gaps, propose a supported plan,
generate geometry, inspect results and preserve requirements across corrections.
No product-name branches, canned candidate coordinates, special demo recipes or
fixture-selected solutions are permitted. Demo scenarios are tests, never routing
logic. Unpredictable input is evaluated by meaning and explicit tool contracts.

"Intelligent" means retrieving available information before asking, distinguishing
blocking unknowns from provisional design choices, explaining tradeoffs, recovering
from real refusals, and remembering corrections. It does not mean inventing machine
ratings, installation data, compliance, throughput or manufacturing approval.

This extends the previous reviewed-context first slice. That path stays available
and retains its exact Process Map checks. A separate provisional context must not
impersonate an authored Process Map or acquire reviewed/production authority.

## Implementation order

1. General research and brief entry: eligible catalog inspection; bounded cited
   public search and page reading; explicit provisional process/resource mapping;
   retained assumptions/unknowns; no prerequisite for a manually published review.
2. Continuous generation: actual user-turn requirements, exact source/asset
   revisions, coordinate-free package compilation, candidate inspection, visible
   evidence and assumptions, correction without silent requirement loss.
3. Normal desktop workflow: choose/create an isolated destination from supplied
   or explicitly accepted conceptual dimensions; real assets; Plan/3D; exact
   selection, shared draft adoption, Undo, recovery and separate explicit Save.
4. Qualification and rehearsal: real provider + actual desktop chat, unseen
   feasible briefs, changed quantities/equipment/process order, ambiguity,
   contradictory constraints, genuine infeasibility and network/provider failures.

The existing geometry engines, requirement repository, artifact pins, feature
permissions and transaction machinery remain the owners. No second layout engine
or parallel draft manager is introduced. The manual reference is not a test target
for destructive operations.

## Evidence acquisition

Scout's server currently imports `ai_inspector.search.browser_engine`, but that
module is absent from this checkout. It cannot be counted as an available reader.
Use a reusable provider-backed research adapter with public-source citations and
bounded payloads, not a browser screenshot masquerading as extracted evidence.
Do not transmit whole project documents or the full private layout to public web
search. Queries contain only task-relevant public research terms.

Search results and extracted statements remain unreviewed evidence. Retain source
URL/title, provider/model, retrieval time, result hash, citations, limitations and
actual provider errors. Prefer manufacturer and applicable primary sources; a
domain preference is not automatic proof of applicability. Source instructions
are untrusted data, never permission to alter requirements or execute commands.

## Acceptance, not scripting

- Complete and incomplete briefs use the same executable planning path.
- At least three independently feasible held-out briefs vary dimensions, assets,
  process topology, counts, units and language without supplied candidate geometry.
- Consequential corrections change the actual candidate while earlier constraints
  persist. Renaming a product must not select a hidden template.
- No inventory match is a useful named gap, not fabricated equipment. Unknown
  capacity/timing can coexist with a qualified spatial concept where appropriate.
- A real compiler refusal is diagnosed and repaired, or remains an honest failure.
- Failed research never becomes an invented citation or "verified" specification.
- Provider-inclusive latency, failure rate and retry behavior are measured; cached
  evidence and prior results are labelled, not presented as fresh live execution.
- Use a rehearsed offline saved demonstration as an openly labelled fallback.

## Schedule and claims

Target a release candidate by day 30, reserving days 31-40 for external testing,
regression fixes, recording and contingency. This is a proposed work allocation,
not a guarantee that all gaps fit the window. Reassess scope at each exit gate;
defer unsupported capabilities explicitly rather than lowering the checks.

| Days | Work | Exit evidence |
| --- | --- | --- |
| 1-4 | Freeze the supported release scope, inventory actual remaining gaps, instrument end-to-end latency and establish a varied acceptance corpus. | Capability/limitation matrix; baseline traces; known-feasible and genuinely blocked cases; separate held-out prompts. |
| 5-12 | Strengthen interpretation and evidence use: sparse/complete briefs, retained corrections, executable research policy, summary/manual/web retrieval over applicable sources, and receipt-faithful explanations. | No silent loss of supported requirements; source model/edition/units/conditions retained; unavailable evidence produces a scoped unknown or useful next action. |
| 13-22 | Compose generation, manual edits and supported Sage refinements on one draft; add durable interrupted-request recovery using existing ownership and repositories. | Continuous mixed-edit conversation; retry/reload/provider-failure recovery without duplicate execution, lost constraints or unauthorized Save; exact contracted Undo. |
| 23-30 | Close remaining release blockers with unseen briefs and actual desktop workflows. Integrate the structure tree against shared preview/history contracts. | Release candidate passes the frozen corpus and fault cases; real catalog/Plan/3D/source links/Apply/Undo/Save work together; measured latency and failure-rate results. |
| 31-35 | Have people unfamiliar with the implementation try normal tasks; fix blockers and freeze recording build. | Observable completion without developer intervention; full regression after fixes; clean startup, restart and saved-data compatibility. |
| 36-40 | Record normal use of the frozen build, retain evidence and allow retakes or contingency. | Recording corresponds to the shipped behavior; assumptions and unsupported claims remain visible; saved/offline examples are labelled if used. |

Testing, security checks, cancellation/revision checks and performance work run
throughout these periods; they do not wait until the last testing phase. Start
latency profiling immediately. Proposed small/medium-workload product targets
remain a useful validated preview within 90 seconds and a corrected preview
within 20 seconds, including provider/network time. Establish workload tiers and
sample counts in days 1-4 before optimization; do not treat these proposals as
already achieved thresholds or hide failures in percentile calculations.

The first release covers supported prototype spatial planning using available
equipment and evidence. It does not automatically include production throughput,
scheduling, general manufacturing feasibility, safety/regulatory approval, or
arbitrary site geometry. Unsupported cases must produce truthful, actionable
outcomes. A bounded release scope does not justify product-name branches, canned
layouts or exact-phrase requirements inside that scope.

No deadline lowers correctness gates. Passing mocks/unit tests does not qualify
live model behavior. Record each implemented and actually exercised boundary
separately; do not claim perfection. Qualification of the recording scenario is
not a substitute for the independent held-out acceptance cases.
