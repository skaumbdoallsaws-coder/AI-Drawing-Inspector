# Facility Layout P11 Self-Use Soak Procedure

## Two Separate Gates

The P11 verifier records two different activities:

1. Accelerated deterministic soak: executable transaction and persistence
   mechanics completed in minutes.
2. Real elapsed soak: actual self-use over at least `14 * 24 hours`
   (1,209,600 continuous elapsed seconds).

Accelerated activity never increments the real elapsed observations.

Exact idempotent replay means retrying the same approved binding, principal,
session, and idempotency key returns the original canonical receipt. Changing
any bound value is an altered retry and must fail closed.

## Accelerated Coverage

The automated harness must exercise:

- At least 10 layouts.
- At least 20 proposal previews.
- At least 10 explicitly approved, receipt-backed applies.
- At least 5 byte-identical dismissals.
- At least 5 rejected stale or unauthorized attempts.
- At least 5 reopen cycles per layout.
- Durable canonical receipt retrieval and idempotent replay.
- A warehouse storage zone and a manufacturing workcell.

Its result appears under `acceleratedDeterministicSoak`.

## Real Elapsed Coverage

The real ledger requires:

- At least 1,209,600 continuous elapsed seconds from the campaign start.
- 10 layouts.
- 50 editing sessions.
- 20 agent previews.
- 10 approved receipt-backed Sage applies.
- 5 dismissed previews proven byte-identical.
- 5 stale or unauthorized attempts rejected.
- 5 reopen cycles for every layout.
- Warehouse, manufacturing-cell, and rollback workflows.
- The same write-capable build throughout the credited interval.

Real observations live only in the source-bound, hash-chained runtime ledger:

```text
.runtime/facility_layout/p11-real-soak-events.json
```

Start it only after the write-capable build is committed and frozen:

```powershell
python tools/record_facility_layout_soak.py start
python tools/record_facility_layout_soak.py status
```

Record actual activity with `record` and the required evidence arguments. Use
`python tools/record_facility_layout_soak.py record --help` for the exact
fields. Approved applies must point to a durably retrieved canonical receipt;
record them with `--receipt-id`. The recorder resolves that ID from the
application's configured canonical transaction store; the CLI cannot select
another store or accept an arbitrary receipt JSON file. The receipt must carry
the approval fingerprint generated by the transaction kernel from the exact
explicit approval consumed by the atomic apply. Dismissals require before/after
files; reopens require the retrieved
layout file and revision. Generated `p11-soak-ledger.json` is a projection and
is never an input to later counts.

Before the full `14 * 24 hours` have elapsed, even if the calendar date has
advanced by fourteen dates, the status must remain exactly:

```text
elapsed_duration_pending
```

After fourteen days, it remains `activity_requirements_pending` until every
count and canonical-receipt check is met.

## Integrity Rules

- Do not backdate `startedAtUtc` or event timestamps. The recorder exposes no
  timestamp override; campaign and event timestamps come from its runtime
  UTC clock, and event time must be monotonic.
- Do not edit the runtime ledger. Campaign metadata, including
  `startedAtUtc`, requirements, and the frozen build identity, forms the
  genesis hash; every event extends that chain, which is verified on every
  read.
- Do not continue crediting a campaign after any write-capable Facility
  Layout source changes, including nested workflow modules; the recursive
  source identity changes and a new campaign must be started.
- Do not count automated accelerated activity as self-use.
- Do not count a preview that was never displayed for review.
- Do not count an apply without explicit approval and a canonical receipt.
- Do not count a reopen unless the saved revision and receipts were retrieved.
- Preserve defects and failed attempts in the pilot issue log.
- A stale proposal rejected by design is evidence; a stale proposal applied is
  a release-stopping defect.
- Generated release JSON is only a projection. Editing it never changes soak
  counts or the runtime ledger.
